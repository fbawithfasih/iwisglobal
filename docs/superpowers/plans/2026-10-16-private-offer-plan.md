# Private Offer Page (payment link for one customer) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A private, unguessable page where one customer (first user: Mr Petersen, 2 travellers, Taj Mahal sunrise tour with Agra Fort on 16 Nov 2026) sees a clear itinerary, picks one of two priced options and a guide language, pays 100% or a 40% booking amount online in EUR, can later pay the balance on the same page, and can download a branded, watermarked PDF itinerary.

**Architecture:** Two new tables hold the offer (content, options, terms) and its payments. All amounts are computed on the server from the stored offer by a pure module; Razorpay orders carry `{kind:'offer', offerPaymentId}` in their notes and are verified like the tour and hotel payments, with the webhook as backstop. The page is server-rendered with one React island for the payment form. The PDF is generated by a generic script (headless Chrome) from a local offer JSON file kept out of git.

**Tech Stack:** Astro 4 hybrid on Cloudflare Pages + D1, React island, Razorpay, Resend. Tests: esbuild bundle + node scripts with in-memory `node:sqlite` and stubbed `fetch` (no framework). PDF: Google Chrome headless (`--print-to-pdf`), already installed at `/Applications/Google Chrome.app`.

**Spec:** this document (design agreed with the owner in chat on 2026-10-16).

## Global Constraints

- Commands run from the repo root `/Users/fasihuddinahmer/Projects/iwisglobal`. `npx astro check` must report 0 errors in `src/`; `npm run build` must pass.
- Customer-identifying data (names, email, phone, the offer JSON, the PDF) is NEVER committed to git. The repo holds only generic code and the schema file. The offer is inserted into production by the owner-approved insert; the PDF and the local offer JSON live in the session scratchpad.
- The offer link is `/offer/<id>` where `<id>` = `po_` + 32 random hex characters (128 bits). The page returns 404 for unknown or closed ids, is `noindex`, and never lists or links to other offers.
- All money is in integer minor units (cents). Razorpay amounts are exactly these minor units. Currency is stored on the offer (here `EUR`).
- Amounts, option, guide language, payment kind and the 40% rule come ONLY from the stored offer and stored payments; nothing price-related from the browser is trusted.
- Pricing rules (owner decisions): option 1 Innova HyCross total 25000 (EUR 250); option 2 Mercedes/BMW sedan total 42500 (EUR 425); German guide adds 1000 (EUR 10) to the total, English adds 0; the booking amount is 40% of the total (rounded to a whole cent); the balance is total minus the deposit paid. German total examples: 26000 (deposit 10400) and 43500 (deposit 17400).
- Itinerary facts (owner decisions): pickup at Shangri-La Eros Hotel, New Delhi between 03:00 and 03:30 (exact time confirmed the evening before); guide English or German (guest's choice); entry tickets for the Taj Mahal and Agra Fort for 2 travellers are included; lunch at the Oberoi is booked by the guests themselves; cancellation line: "Free cancellation up to 24 hours before pickup" with a link to `/cancellation-refund-policy`.
- Guest-facing text is English only for this feature (a private offer for one English-speaking guest); the page chrome uses plain constants, the offer content comes from the offer row.
- Commits: no attribution lines. No push, no production database change, no `wrangler` without the owner's explicit yes.
- Env: Razorpay keys are already available through `resolveEnv` (`PUBLIC_RAZORPAY_KEY_ID`, `RAZORPAY_KEY_SECRET`, `RAZORPAY_WEBHOOK_SECRET`); no new secrets.

## Review Focus

1. A guest double-clicks Pay, closes and reopens the Razorpay window, or pays twice: exactly one paid payment per kind; a stray second payment raises an owner alert and is never silently accepted (Task 2 tests).
2. Verify and the Razorpay webhook both arrive: one recorded payment and one set of emails (Task 2 tests).
3. Wrong amount, wrong currency or wrong order id on a captured payment: no state change, owner alert (Task 2 tests).
4. After a 40% payment the balance button works once, only for the option and language already paid for, for exactly total minus deposit; paying "full" after a deposit is refused (Task 1 tests).
5. The page never reveals another customer's data, and an unknown or malformed id gives a plain 404 (Task 3).

```sql
-- Private offer pages (one secret link per customer). Run once:
--   wrangler d1 execute iwisglobal-bookings --remote --file=schema_private_offers.sql
CREATE TABLE IF NOT EXISTS private_offers (
  id TEXT PRIMARY KEY,                       -- 'po_' + 32 hex: the secret in the link
  status TEXT NOT NULL DEFAULT 'open',       -- open | closed
  customer_name TEXT NOT NULL,
  customer_email TEXT NOT NULL DEFAULT '',
  customer_phone TEXT NOT NULL DEFAULT '',
  currency TEXT NOT NULL,                    -- EUR | USD | INR
  content_json TEXT NOT NULL,                -- title, summary, date, travellers, pickup, hotel, itinerary[], includes[], excludes[], cancellation
  options_json TEXT NOT NULL,                -- [{id,label,vehicle,totalMinor}]
  deposit_percent INTEGER NOT NULL DEFAULT 40,
  german_guide_extra_minor INTEGER NOT NULL DEFAULT 0,
  created_at TEXT NOT NULL
);

CREATE TABLE IF NOT EXISTS offer_payments (
  id TEXT PRIMARY KEY,                       -- 'op_' + uuid
  offer_id TEXT NOT NULL,
  option_id TEXT NOT NULL,
  guide_language TEXT NOT NULL,              -- en | de
  kind TEXT NOT NULL,                        -- full | deposit | balance
  amount_minor INTEGER NOT NULL,
  total_minor INTEGER NOT NULL,              -- trip total at the time of the order
  currency TEXT NOT NULL,
  order_id TEXT NOT NULL DEFAULT '',
  payment_id TEXT NOT NULL DEFAULT '',
  status TEXT NOT NULL,                      -- created | paid
  payer_name TEXT NOT NULL DEFAULT '',
  payer_email TEXT NOT NULL DEFAULT '',
  payer_phone TEXT NOT NULL DEFAULT '',
  created_at TEXT NOT NULL,
  updated_at TEXT NOT NULL
);
CREATE INDEX IF NOT EXISTS idx_offer_payments_offer ON offer_payments (offer_id, status);
CREATE UNIQUE INDEX IF NOT EXISTS idx_offer_payments_payment ON offer_payments (payment_id) WHERE payment_id != '';
```
